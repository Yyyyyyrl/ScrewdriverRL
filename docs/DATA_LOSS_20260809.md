# Data loss — 2026-08-09 working-tree truncation

**Status:** unresolved. Seven tools are gone; two survive only in an older form.
Read this before touching the free-cube (in-hand cube rotation) pipeline.

## What happened

At **2026-08-09 12:56** every file in a large slice of the working tree was truncated to
zero bytes and its mode flipped `644 → 755`. The cause was never identified; the uniform
timestamp and the mode flip point at a bulk copy through a filesystem that dropped both
content and permissions (an external drive, a container mount, or an interrupted `rsync`).

The damage was not noticed for two days because git reported the files as *modified*
rather than deleted — they still existed, they were just empty.

## How to avoid a repeat

1. **Commit tool scripts as soon as they work.** Every permanently lost file here was one
   that had never been committed. Untracked means unbacked-up.
2. **Never `git checkout .` or `git restore .` across the whole tree** when the state is
   unclear. Check for zero-byte tracked files first:
   ```bash
   git ls-files | while read f; do [ -s "$f" ] || echo "$f"; done
   ```
   Empty output means the tree is healthy.
3. **A file that git calls "modified" can be an empty file.** `git status` alone will not
   tell you; compare sizes against `HEAD` when a diff looks implausibly large.
